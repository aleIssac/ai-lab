# 模型部署指南

## 模型文件的保存与加载

PyTorch 有两种保存方式。推荐保存 `state_dict` 而不是整个模型对象：

```python
torch.save(model.state_dict(), "model.pt")
model.load_state_dict(torch.load("model.pt"))
```

直接 torch.save 整个模型会序列化类的路径，一旦代码重构或目录变动就会加载失败。保存 state_dict 只存参数张量，更稳定，但加载时必须先实例化同结构的模型。

保存时还要把预处理参数一起存下来，比如标准化的均值方差、词表、类别编码映射。推理时如果预处理和训练时不一致，模型会静默地给出错误结果，这是线上问题最常见的来源之一。

## 用 FastAPI 封装推理服务

一个最小的推理服务包含三部分：启动时加载模型、定义请求体的数据结构、实现预测接口。

启动时加载只需执行一次，放在模块级别。预测接口接收 JSON，转换成模型需要的张量格式，调用模型，再把结果转回 JSON 返回。

几个实践要点。第一，服务启动后第一次请求会较慢，因为要初始化算子，可以在启动时用一条假数据预热。第二，推理要放在 `torch.no_grad()` 下，减少内存占用。第三，输入要做合法性校验，用 Pydantic 定义字段类型和范围，避免脏数据直接进入模型。

## Batch 推理与吞吐优化

单条推理的吞吐很低。如果有批量请求，应该合并成一个 batch 送进模型。对于 Transformer 类模型，可以用动态批处理（dynamic batching）把短时间内到达的请求攒在一起。

另一个优化点是模型量化。把 FP32 权重转成 INT8，模型体积减为四分之一，推理速度通常提升两到四倍，精度损失一般在百分之一以内。PyTorch 提供了训练后量化（post-training quantization）的接口。

如果对延迟要求极高，可以考虑导出成 ONNX 格式，用 ONNX Runtime 推理，或者进一步用 TensorRT 优化。

## 服务的可观测性

上线后至少需要监控三类指标。第一类是业务指标，比如每天的请求量、预测结果的分布，如果分布突然偏移说明数据可能变了。第二类是性能指标，包括 P50 和 P99 延迟、QPS、错误率。第三类是资源指标，GPU 利用率和显存占用。

日志要记录每次请求的输入摘要和输出，方便事后排查。但要注意脱敏，不要把用户隐私数据写进日志。

## 灰度发布与回滚

新模型不要直接全量替换。先让小比例流量走新模型，对比两边的指标，确认无异常后再逐步扩大。这需要一个流量切分机制，通常按请求 ID 哈希或者用户 ID 分组。

回滚能力必须提前准备好。模型文件要版本化保存，配置里指定当前使用的版本号，出问题时改配置重启就能回退。不要用覆盖式更新模型文件。

## 常见上线事故

第一类是训练和推理的特征处理不一致。比如训练时对缺失值填了中位数，线上代码忘了填，或者用了不同的中位数。解决办法是把预处理固化成一个对象随模型一起保存。

第二类是数据漂移。上线几个月后用户行为变化，输入分布偏离训练分布，模型效果下降。需要定期统计输入特征的分布，和训练时对比。

第三类是显存溢出导致的雪崩。并发上来后显存不够，请求排队，超时重试又加剧压力。要设置合理的并发上限和超时时间。
